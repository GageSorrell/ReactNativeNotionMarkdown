# react-native-notion-markdown documentation

This workspace contains the versioned Astro documentation website for `react-native-notion-markdown`.

## Prerequisites

Run commands from the repository root with the Node.js version declared by the repository's `.nvmrc` file. Install the monorepo dependencies before working on the site:

```sh
npm install
```

The documentation workspace is private and is addressed by its npm workspace name:

```sh
npm run dev --workspace Documentation
```

## Write documentation

Documentation pages are MDX files under `src/content/docs/<version>/`. The current version is `v1`, with onboarding pages in `src/content/docs/v1/onboarding/` and longer guides in `src/content/docs/v1/guides/`.

Create a page with YAML frontmatter containing at least a `title`. Use `description` for page metadata and `sidebar.order` to control ordering within a sidebar group:

```mdx
---
title: Working with documents
description: Parse, transform, and serialize a document.
sidebar:
  order: 6
---

Explain the feature here.

## A useful subsection

Add examples and links that help a reader complete the task.
```

The page URL is derived from its file path. For example, `src/content/docs/v1/guides/renderer.mdx` is available at `/docs/v1/guides/renderer`.

Use normal Markdown and fenced code blocks for most content. MDX components are available through the local Starlight-compatible shim:

```mdx
import { Aside, Badge, Steps, Tabs, TabItem } from '@astrojs/starlight/components'

<Aside type="note" title="Important">
  Keep this guidance short and actionable.
</Aside>

<Badge text="Experimental" variant="caution" />
```

The supported `Aside` types are `note`, `tip`, `caution`, and `danger`. `Tabs` contains one or more `TabItem` components, and `Steps` should wrap an ordered list.

Link to another documentation page with its versioned path, for example `/docs/v1/guides/document-model`. Link to the repository's format specification when documenting syntax instead of duplicating the specification in the website.

### Add a new version

Create a new content directory such as `src/content/docs/v2/`, then add the version to `src/lib/versions.ts`:

```ts
export const DOCS_VERSIONS = [
    { value: "v2", label: "v2" },
    { value: "v1", label: "v1" }
] as const;
```

Add matching `v2` entries to `src/content/docs/sidebar-config.json` and `src/content/docs/onboarding-groups.json`. The onboarding JSON references document IDs such as `v2/onboarding/introduction`. Add or update a redirect in `astro.config.ts` if an older URL should point to the new version.

### Configure the sidebar

`sidebar-config.json` stores the order of automatically generated guide groups for each version:

```json
{
  "v1": {
    "onboarding": 1,
    "guides": 2
  }
}
```

`onboarding-groups.json` defines curated onboarding groups and their document IDs. Documents not referenced by onboarding are grouped automatically by their directory, so adding a guide normally requires only creating the MDX file and setting its `sidebar.order`.

## Configure the website

The main configuration files are:

- `astro.config.ts` configures Astro integrations, the Tailwind Vite plugin, fonts, redirects, heading IDs, and heading permalink generation.
- `content.config.ts` defines the docs, sidebar, and onboarding content collections. `src/content.config.ts` re-exports it for Astro's content tooling.
- `src/styles/global.css` contains the Tailwind theme tokens, light/dark color variables, typography, prose styles, and responsive layout rules.
- `src/lib/versions.ts` is the source of truth for supported documentation versions.
- `src/lib/navigation.ts` contains the GitHub and npm links used by the site chrome.
- `public/favicon.svg` and `src/assets/logo.svg` contain the site branding.

The site is a static Astro build. Search is generated by the `postbuild` lifecycle script, so deployment must run the workspace `build` script rather than invoking `astro build` alone:

```sh
npm run build --workspace Documentation
```

The generated website is in `Documentation/dist/`, and the generated Pagefind assets are in `Documentation/dist/pagefind/`. Do not commit `dist/` or `.astro/`; both are ignored by `Documentation/.gitignore`.

## Develop and verify locally

Start the development server with:

```sh
npm run dev --workspace Documentation
```

The root route redirects to the current documentation version. Pagefind is not available in the Astro development server, so test search against a production build:

```sh
npm run build --workspace Documentation
npm run preview --workspace Documentation
```

Run the static checks before opening a pull request:

```sh
npm run typecheck --workspace Documentation
npm run lint --workspace Documentation
npm run build --workspace Documentation
```

When reviewing a page, check its sidebar entry, heading permalink links, table of contents, previous/next navigation, responsive mobile menu, dark/light theme toggle, and Pagefind result if the page contains searchable content.

## Deploy the website

The build is provider-neutral static output. A deployment service needs the repository root as its checkout, Node.js configured to the repository version, `npm ci` as the install command, `npm run build --workspace Documentation` as the build command, and `Documentation/dist` as the publish directory.

For a local or self-managed deployment, build the site and copy the contents of `Documentation/dist/` to the document root of the static web server:

```sh
npm ci
npm run build --workspace Documentation
```

The server must serve `index.html`, preserve the generated `/pagefind/` directory, and support the generated directory-style page paths. Configure the host to fall back to `404.html` for unknown routes if it supports a custom not-found page.

For a provider that uses `Documentation` as the project root, use `npm ci`, `npm run build`, and `dist` instead. In either setup, make sure the provider runs the full npm build lifecycle so the `postbuild` Pagefind step executes.

If the site will be hosted below a path such as `/documentation`, configure Astro's `base` and `site` values in `astro.config.ts` before deploying, then rebuild and verify every internal link and the `/pagefind/` URL under that base path. A custom domain served from the web root does not need a `base` path.

## API references

The References section is generated from the package export map, so the website documents the public `react-native` target of each code-bearing export and never documents `./package.json`. The current configuration is in `Script/ApiReference/src/config.ts`; it defines the package group, repository, supported reference channels, and the ordered nine-module allowlist.

Run the generator from the repository root when you want to inspect the current checkout:

```sh
npm run api:generate --workspace Documentation
npm run api:validate --workspace Documentation
npm run build --workspace Documentation
```

Generated files are stored under `Documentation/.data/api-reference/<version>/` and are ignored by Git. A dataset contains the export/module manifest, TypeDoc JSON, source revision metadata, normalized module records, and SHA-256 checksums. `npm run build --workspace Documentation` regenerates the dataset before Astro builds; CI builds that use a published snapshot run `npm run build:snapshot --workspace Documentation` so restoration is not overwritten.

### Author JSDoc for references

Put the public description immediately above an exported declaration and use normal Markdown in the summary. `@since`, `@see`, and `@example` are supported and are rendered on the declaration page. `{@link Symbol}` and `{@linkcode Symbol}` are accepted in comments, and fenced Markdown, tables, and ordinary inline Markdown are passed through the reference comment renderer. Keep comments focused on the public contract and avoid documenting private, protected, internal, or `@internal` implementation details.

```ts
/** Parse a Notion-flavored markdown document.
 *
 * @since 1.0.0
 * @see serializeNotionMarkdown
 * @example
 * ```ts
 * const result = parseNotionMarkdown(markdown)
 * ```
 */
export function parseNotionMarkdown(markdown: string) { }
```

After changing a public declaration or its comments, regenerate the references and run `npm run verify --workspace Documentation`. Declaration anchors are derived from the exported name and should be treated as stable permalinks.

### Publish a new reference snapshot

`v1` is the documentation channel and is independent of the package's npm version. To publish a deterministic snapshot, select a full lowercase 40-character source commit that is an ancestor of `Origin/Master`, then run the `Publish API reference snapshot` GitHub Actions workflow with that commit. The workflow creates an `api-reference-<sha256>` non-latest GitHub release containing `api-reference.tar.gz`, its checksum, and `manifest.json`.

The equivalent local commands are:

```sh
npm run build --workspace @react-native-notion-markdown/api-reference
node Script/ApiReference/dist/cli.js generate --version v1 --source-ref <full-lowercase-commit>
node Script/ApiReference/dist/cli.js validate --version v1
node Script/ApiReference/dist/cli.js snapshot package --version v1
node Script/ApiReference/dist/cli.js snapshot publish --version v1
```

Use `snapshot id` to calculate the tag without generating files. Use `snapshot resolve --tag api-reference-<sha256>` to inspect a release and `snapshot restore --tag api-reference-<sha256>` to download and validate one locally. Snapshot identity includes the schema version, sorted channel-to-source-revision map, and generator digest, so changing any of those inputs creates a different tag.

### Add a package or documentation version

Add a new package only by extending the explicit allowlist in `Script/ApiReference/src/config.ts` with its package directory, repository, channels, and ordered modules. The discovery step will fail if a code-bearing export is present in `package.json` but is not configured, which prevents accidental reference drift. Add a new documentation channel to `DOCS_VERSIONS` in `src/lib/versions.ts`, create its guide content and sidebar JSON entries, and add the channel to the package reference configuration before generating its dataset.

When a new `react-native-notion-markdown` version is published, update the package source and export map, select the intended source commit, publish the snapshot, and then deploy the website with that exact snapshot tag. A normal `Master` deployment restores the newest valid `api-reference-*` release automatically; the production workflow also accepts an explicit tag for a controlled release or rollback.

## Customize the website

Update navigation labels, GitHub/npm links, or the References tab in `src/lib/navigation.ts` and `src/components/navigation/DocsNavigation.astro`. Change the supported versions in `src/lib/versions.ts`. Guide grouping and onboarding order are controlled by `src/content/docs/sidebar-config.json` and `src/content/docs/onboarding-groups.json`.

The visual theme is defined in `src/styles/global.css`. Change the light and dark CSS variables in `:root` and `.dark` for colors, update the `@theme` mappings for Tailwind utilities, and adjust typography or responsive rules in the same file. The site already supports the system preference plus the persisted light/dark theme toggle; new components should use the existing `background`, `foreground`, `muted`, `muted-foreground`, `border`, `accent`, `code-background`, and `code-foreground` tokens so both variants remain consistent. Markdown code blocks use the `github-light`/`github-dark` Expressive Code themes configured in `astro.config.ts` and switch from the root `data-theme` value when the theme toggle is used. Fonts, heading permalink generation, redirects, and integrations are configured in `astro.config.ts`.

Reference pages use `src/components/api/`, `src/pages/docs/[version]/api/`, and the custom `apiReference` loader in `content.config.ts`. Keep generated data out of source files and make presentation changes in these components instead of editing `.data` records.

### Customize the landing page

The public home page is `src/pages/index.astro`. It composes the reusable landing components in `src/components/landing/` with the typed `LANDING_CONFIG` in `src/lib/landing.ts`. Change package copy, links, install commands, comparison panels, capability cards, statements, and FAQs in that configuration instead of embedding package-specific content in the components.

The landing page follows the section rhythm of the cloned Effect website in `EffectDocs/apps/web`, but its copy and package data are specific to this repository. `LandingHero`, `LandingExamples`, `LandingTestimonials`, `LandingProblem`, `LandingMentalModel`, `LandingCodingWithAi`, `LandingQuotes`, `LandingFaq`, and `LandingCallToAction` own the reusable section layouts. `LandingInstallCommand` owns the package-manager dropdown, icons, copy feedback, and keyboard behavior. `LandingGridBackground` provides the repeating light/dark grid used by the hero and final CTA, while `LandingGridRails` provides the desktop container rails. The source visual-effects runtime is not copied: the examples area uses a static pipeline panel while retaining the nested Start/Scale comparison tabs.

The landing styles live in `src/styles/landing.css` and use the same light/dark tokens as the documentation site. Keep new package configurations compatible with `LandingPageConfig`, and reuse `LandingTabs` and `LandingTabPanel` for static, keyboard-accessible tab groups. Nested tab groups have independent state; matching `syncKey` values can synchronize related groups when that is useful. The landing tabs intentionally do not include visual-effect animations, canvas code, or animation-specific dependencies. The header uses the same `ThemeToggle` as the docs site; theme state is persisted in `localStorage` under `theme` and follows the system preference until a user chooses a mode.

To add a future package, create another configuration that implements `LandingPageConfig`, pass it to `LandingPage` from a package-specific route, and provide that package's logo, links, documentation paths, install commands, and content. The existing docs `Tabs` and `TabItem` components remain available to MDX pages and now support stable IDs, keyboard navigation, and optional synchronization keys.

## Vercel setup and deployment

The repository root is linked to the Vercel project `sorrell/react-native-notion-markdown`. The link is stored in the ignored `.vercel/project.json` file, so each collaborator should run `vercel login` and `vercel link` from the repository root once. `vercel.json` pins the Astro output to `Documentation/dist`, `.nvmrc` selects Node 24, and the normal Vercel build regenerates the API dataset from the checked-out package source.

For a direct local deployment, run:

```sh
vercel pull --yes --environment=production
vercel --prod
```

The first command downloads the linked project's settings and environment variables; the second runs the configured build and promotes the result to production. Use `vercel` without `--prod` for a preview deployment. Add `PUBLIC_SITE_URL` as a repository or Vercel environment variable so canonical and Open Graph URLs use the deployed origin.

The repository also supports deterministic snapshot deployments through GitHub Actions. The production and rollback workflows restore an exact API snapshot, then use `vercel.snapshot.json` with the pinned `vercel@59.25.0` CLI so the restored dataset is not regenerated during the Vercel build. Configure the Vercel project with automatic Git deployment disabled when using these workflows, then add the repository secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and `VERCEL_PROJECT_ID`. Preview deployments run for same-repository pull requests when those secrets are available; fork pull requests retain all checks and skip credentialed deployment. Production deploys run on every `Master` push, restore the latest published API snapshot, smoke-test the API landing page, an OG PNG, and Pagefind, and then promote the verified deployment.

Run the same checks locally before changing deployment settings:

```sh
npm run typecheck --workspace Documentation
npm run lint --workspace Documentation
npm run build --workspace Documentation
npm run verify --workspace Documentation
```

To update the Vercel project settings or inspect the current deployment, use `vercel project ls`, `vercel inspect <deployment-url>`, and `vercel logs <deployment-url>`. Do not commit `.vercel/` or `.env.local`; both are local Vercel state and are already ignored.

To roll back, run the `Roll back documentation` workflow with an ancestor website commit and the exact `api-reference-<sha256>` snapshot tag. It rebuilds that deterministic pair, performs the same smoke test, and promotes the deployment only after verification.
